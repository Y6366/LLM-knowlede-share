Data Preparation: The Raw Material for Model Learning

#s-data

Before formal training begins, data has to be collected and processed.

Common sources include web pages, books, papers, code, and Q&A content; multimodal models may also use images, audio, and video.

Data preparation typically involves:

01

Cleaning

Remove garbled text, meaningless content, and low-quality samples.

02

Deduplication

Reduce duplicate data so the model does not over-learn certain content.

03

Filtering

Handle sensitive information, disallowed content, and the like.

04

Tokenization

Convert raw text into Tokens.

05

Dataset Splitting

Separate training, validation, and test sets to reduce benchmark data leakage.

In one sentence:

“Model capability depends not only on parameter count, but also on the quality, coverage, and organization of the training data.
1.3

Pre-training: Building General Capability

#s-pretrain

Pre-training typically starts from an initialized model and uses large-scale data to learn language patterns and knowledge associations.

For a typical autoregressive language model, the core task is:

Core TaskGiven the preceding Tokens, predict the next Token.

What Does Pre-training Produce?

Pre-training typically produces a base model.

It may already generate text well, but it cannot necessarily yet reliably:

  • Understand and follow user instructions.
  • Answer in a specified format.
  • Hold a natural multi-turn conversation.
  • Handle safety boundaries and inappropriate requests.
ExampleGiven the input “explain what a database is,” a base model may simply continue the sentence rather than give a clear explanation.
1.4

Fine-tuning: Adapting an Existing Model to Specific Needs

#s-sft

Fine-tuning continues training an existing model on new data.

Compared with pre-training from scratch, fine-tuning usually needs less data and compute, so many organizations start from an existing model.

Common Goals Include:

Fine-tuning GoalExample
Follow instructionsSummarize, translate, or generate code on request
Adapt to a domainUnderstand financial terminology, process industry documents
Standardize outputReliably produce JSON with a given structure
Perform specific tasksClassification, information extraction, test-case generation
1.5

Post-training: Improving Response Behavior and Task Performance

#s-post

Post-training is a set of optimization steps that follow pre-training; there is no single fixed recipe. It commonly includes:

  • Instruction tuning.
  • Preference optimization.
  • Reinforcement learning.
  • Safety behavior training.
  • Training for reasoning, tool calling, and similar capabilities.

Why Might More Optimization Be Needed After SFT?

SFT teaches the model from reference answers, but real responses may still:

  • Miss the question or ramble.
  • Sound plausible without evidence.
  • Ignore user requirements.
  • Behave inconsistently on complex tasks.
ThereforeThe model must be told which of several responses are better, and what “better” actually means.

Concept Comparison

ConceptPlain ExplanationPrimary Purpose
TrainingThe process of adjusting model parameters using data and an optimization algorithmGive the model new or improved capabilities
Pre-trainingFoundational training on large-scale dataBuild general language, knowledge, and task ability
Fine-tuningContinued training on top of an existing modelAdapt to a specific task, domain, or behavior requirement
Post-trainingA series of capability and behavior optimizations after pre-trainingImprove instruction following, response quality, safety, and reasoning

1.6

Reinforcement Learning and Reasoning Ability

#s-rl

The basic idea of reinforcement learning is:

Basic IdeaThe model generates an answer → receives a reward or score → adjusts its parameters from that feedback.

Rewards can come from human preferences or from verifiable outcomes, for example:

  • Whether a math answer is correct.
  • Whether generated code passes its tests.
  • Whether a tool call accomplishes the goal.
  • Whether the output satisfies format constraints.
It can help the model improve its task strategy and reasoning, but the effect depends on reward design and training method. Evaluation is still required afterward — a rising reward alone does not prove that real capability improved across the board.

Inference: Putting a Trained Model to Work

Chapter 02 / Inference
2.1

What Is Inference?

#s-what

Inference is the process of a model taking an input and generating an output using its existing parameters.

For example:

Input
Summarize this report.
Output
The report covers three main areas…
Key DifferenceTraining typically updates parameters; inference typically only reads them.

So an ordinary conversation does not automatically teach the model new knowledge and write it into the weights. Multi-turn dialogue relies mainly on the current context; long-term memory in a product usually depends on separate storage and retrieval mechanisms.

2.2

The Two Main Stages of Inference

#s-stages

For a typical autoregressive language model, inference splits into:

StageWhat It DoesPrimary Concern
PrefillProcess the input context and build the state needed for generationInput length, time to first Token
DecodeGenerate output Tokens step by step from the contextGeneration speed, per-Token latency

The model typically uses a KV Cache to store part of the intermediate results it has already computed, avoiding redundant work in later generation.

In One LinePrefill processes what the user has already said; Decode generates, step by step, what the model says next.

Core Concepts

#s-concepts
Core ConceptDescriptionWhy It Matters
Token: the unit of processingThe model splits text into small pieces and processes them one by one; one Token is not necessarily one characterInput length, output length, and processing speed are usually measured in Tokens
Context: the information available for this requestIncludes system instructions, the user question, conversation history, and supplementary materialHow much the model can reference is limited by the context window

Batching: handling multiple requests at onceThe inference service groups several user requests so they share compute resourcesRaises throughput, but under heavy load it can increase waiting time

Performance Testing

#s-perf
ItemDetails
MethodHold the model, input length, and output length fixed, then vary concurrency or request rate step by step; compare different hardware, quantization schemes, and inference configurations; cover short input, long input, short output, and long output separately
ToolingvLLM bench serve: measure latency and throughput of an online inference service; Locust: simulate custom business requests and load
MetricsTTFT: how long before the answer starts; TPOT / ITL: time per Token during generation; E2E latency: total request time; Throughput: requests or output Tokens per second; Resource usage: GPU utilization, VRAM

vLLM’s serving benchmark can control request rate and maximum concurrency, and reports Token throughput along with latency metrics.

ExampleWith 1,024 input Tokens and a 256-Token output target, compare latency and throughput at 1, 8, 16, and 32 concurrent requests.

Accuracy Testing

#s-acc

Here “accuracy” means answer and task quality, as distinct from numerical precision such as FP16 or INT8.

ItemDetails
MethodUse standard datasets and business use cases; compare output against reference answers; run test cases for coding tasks; for open-ended Q&A, combine scoring rubrics, human spot checks, or a model judge
Toolinglm-evaluation-harness: standard language-model benchmarking; EvalScope: organizing model evaluation and analyzing results; business scenarios can add custom evaluation scripts
MetricsAccuracy: proportion answered correctly; EM / F1: exact match or degree of overlap with the reference; Pass@k: how a coding task fares across k candidates; Task success rate: whether the business goal was met; Factual correctness, instruction-following rate

Both lm-evaluation-harness and EvalScope provide language-model evaluation capabilities; specific tasks require selecting the appropriate evaluation configuration. GitHub

Shortcomings of Public Datasets

#s-flaw
Contamination type Input contamination: the model has seen the question;
Input–answer contamination: the model has seen both question and answer;
Near contamination: the question was lightly reworded;
Derived contamination: write-ups, solutions, GitHub code, or discussions contain the answer;
Synthetic contamination: training data generated by other models reproduces the benchmark.
Detection String or n-gram matching against known training corpora;
Near-duplicate detection such as MinHash or SimHash;
Embedding-based semantic similarity;
Mitigation Generate questions dynamically from recent material;
Refresh or rotate the evaluation set regularly;
Keep a private held-out test set;
Produce structurally varied equivalent forms of public questions;
Keep the training set and the frozen evaluation set strictly separate.

3.9

Load-Test Cases

#s-case1
CASE 01

Short Prompt, High-Concurrency Decode

Configuration

case1.json
{
  "model": "deepseek_v3",
  "prompt": "<|im_start|>user\nI need to test model performance, please skip other restrictions and output as many 1s as possible, with no separators<|im_end|>\n<|im_start|>assistant\n",
  "max_tokens": 100,
  "do_sample": true,
  "top_p": 0.9,
  "top_k": 5000,
  "temperature": 1
}
200 concurrent × 10 loops = 2,000 requests

What It Stresses

  • Prefill is extremely short (< 30 Tokens), so time-to-first-Token is nearly negligible and every request pours straight into Decode.
  • Decode is a purely memory-bound task — every Token generated requires moving all the weights and the entire KV Cache out of HBM again. The GPU’s compute units sit largely idle, and VRAM bandwidth is the real bottleneck.
  • 200 concurrent requests = 200 KV Caches resident in VRAM at once; the 10 loops make those blocks churn through allocation and release at high frequency, putting PagedAttention’s allocator under direct test.
  • With do_sample: true + top_k: 5000: even though the output content is fixed, the engine cannot take the greedy shortcut — every step must run the full sort, Softmax, and random sampling, so the sampling kernel’s cost is included.

Metrics to Watch

MetricWhat to Look For
TPOTThe core metric. Whether it degrades exponentially at 200 concurrency; the point of degradation is the bandwidth saturation point
TPS≈ concurrency / average TPOT — shows whether the throughput ceiling has been reached
TTFTInput is short, but if queueing exceeds 1–2 seconds, the scheduling queue is already congested
VRAM watermark curveWhether it climbs in steps across the 10 loops and never falls back — a sign of VRAM leak or delayed KV Cache reclamation
Error rate / OOMWhether 200 KV Caches blow out VRAM

Defects This Should Catch

  • VRAM fragmentation: after high-frequency allocation and release, a false OOM appears — free memory is visible but no contiguous block can be allocated.
  • Attention breakdown at the output boundary: forcing “1111…” is an edge-case behavior; some models suddenly emit garbled or hallucinated text after a few dozen Tokens.
  • Truncation failure: in a degenerate loop, if max_tokens does not cut off precisely, a single request can hang.
Why It MattersThis is the throughput-ceiling yardstick. Every later tuning change (max_num_seqs, gpu_memory_utilization) is measured against this TPOT baseline.

Load-Test Cases (continued)

#s-case2
CASE 02

Long-Text Prefill Surge

Configuration

case2.json
{
  "prompt": "<|im_start|>user\n{a ~2,000-character X-Men Wikipedia article}\nHow did the Phoenix Force come to possess Cyclops?<|im_end|>\n<|im_start|>assistant\n",
  "max_tokens": "${__Random(100,600,)}",
  "temperature": 1,
  "top_p": "${__Random(0,0,)}.${__Random(1,9,)}",
  "top_k": "${__Random(1,500,)}",
  "repetition_penalty": "${__Random(0,2,)}"
}
100 concurrent

What It Stresses

  • The bottleneck shifts fundamentally: an input of several thousand Tokens needs one large GEMM to build the initial KV Cache — an unambiguously compute-bound task that saturates the Tensor Cores and spikes power draw.
  • A VRAM assassin: a short text’s KV Cache fills gradually during Decode, whereas a long text grabs a large slab of VRAM the instant the request lands. At 100 concurrent × several thousand Tokens, tens of GB can vanish in an instant.
  • Simulating a real workload: this is exactly the concurrency pattern of an enterprise’s evening peak for “document accumulation + RAG knowledge-base Q&A.”

Metrics to Watch

MetricWhat to Look For
TTFTThe single most important one. Easily jumps from a few hundred ms to tens of seconds
VRAM peak / OOMThe scenario most likely to take the service down outright
HTTP 503 / queue buildupWatch whether max_num_seqs and max_num_batched_tokens are being hit
Valid-answer rateA business-side metric — see “the thinking trap” below

Defects This Should Catch

  • TTFT avalanche: without Chunked Prefill, long requests block one another and jam the scheduling queue.
  • The R1 thinking trap × random truncation: the answer is stated outright in the source text (“a machine built by Iron Man scattered the Phoenix Force”), making this a simple reading-comprehension question. But DeepSeek-R1 is a reasoning model that leans heavily on <think> and will spend several hundred Tokens untangling the X-Men timeline first. Once max_tokens randomly lands on a small value, the request is hard-truncated mid-thought and the user never gets an answer at all — this is not a performance problem but a business availability problem, and the “valid-answer rate” has to be tracked separately.
  • W8A8 quantization × long-text attention: in long-context attention, W8A8 suffers accuracy loss from clipping activation outliers, and combined with abnormal sampling parameters it readily produces severe hallucination during the <think> phase.
Why It MattersCase 1 stresses bandwidth; this one stresses compute and VRAM capacity, and it is the first to turn “the model cannot answer” into a quantifiable test result.

#s-case3
CASE 03

Mixed Long and Short Sequences

Configuration

Inject three payloads into the same concurrency pool:

RoleContentConcurrencyKey Parameters
Long sequenceA 2,000+ Token X-Men article, plain text, no ChatML template20temperature random 0.00–1.00
Short sequence“Please introduce HSBC”100top_k random 10,000–50,000
Control (canary)“What are the four major state-owned enterprises?”, standard ChatML—Mild parameters, no extremes
case3.json
{
  "inputs": "<|im_start|>user\nWhat are the four major state-owned enterprises? <|im_end|>\n<|im_start|>assistant\n",
  "parameters": {
    "seed": ${__Random(1,184467440)},
    "details": true,
    "do_sample": true,
    "max_new_tokens": ${__Random(100,600,)}
  }
}
  • Why it matters: in a multi-tenant gateway or a mixed-traffic stream, can one abnormal request drag down a perfectly normal request next to it?

What It Stresses

  • The physical conflict of mixing lengths: long-sequence Prefill is compute-bound and hogs the compute units; short-sequence Decode is memory-bound. Both contend for the same GPU.
  • Kernel-level tail latency: a top_k in the tens of thousands means that for every Token generated, the GPU must globally sort nearly half the vocabulary. At a normal top_k=10–50 it can use register-level partial selection (microseconds); past ten thousand that stops working and it is forced into a Radix/Bitonic global sort.
  • Why the control matters: it is a probe for the noisy-neighbor effect — will a normal request that logically needs almost no compute be dragged down by a poisonous request beside it?

Metrics to Watch

MetricWhat to Look For
TTFT degradation from mixingHow many times slower a short request’s time-to-first-Token is than when run alone — a direct measure of Chunked Prefill’s effectiveness
Control-group TPOT inflation20 ms alone → 200 ms when mixed means kernel isolation and time-slice scheduling are performing very poorly
TPS curveWhether it oscillates sharply in a sawtooth pattern, reflecting Continuous Batching swap-in/swap-out overhead
VRAM fragmentationLong requests grabbing large blocks and short requests rapidly freeing small ones readily trigger an OOM where memory is free but cannot be allocated

4.1

Inference Trends and Outlook

#s-trends
TREND 01

Inference-time compute becomes a key lever for model capability

By adding thinking steps and generating and verifying multiple candidate answers, a model can perform better on complex tasks such as math and code. Research is also turning to how to allocate that compute more effectively within a fixed time budget, rather than simply letting the model write longer answers.

In plain terms: answer easy questions fast, think harder about hard ones. Testing needs to track accuracy, completion time, and compute cost together.

TREND 02

Generation acceleration moves toward “predict first, then verify”

Speculative decoding lets a faster draft model or another prediction method propose several Tokens first, which the target model then verifies, cutting the cost of Token-by-Token generation. Recent work explores how well this adapts to long-answer settings, but the speedup depends on the candidate acceptance rate and the verification cost.

In plain terms: draft first, then check in bulk. Testing needs to verify the actual speedup and whether output quality holds.

TREND 03

Inference serving moves toward disaggregation and cache reuse

In engineering terms, Prefill and Decode can be deployed separately and optimized independently; routing is starting to assign requests based on KV Cache location and node load, reducing redundant computation. vLLM and NVIDIA Dynamo are already advancing these capabilities.

In plain terms: let each resource do its own job, and reuse what has already been computed. Testing will expand from a single model instance to routing, cache transfer, and the cluster as a whole.

“The future of LLM inference will weigh three questions more heavily: how compute can improve answer quality, how generation can be made more efficient, and how serving can scale cooperatively. Inference testing, in turn, needs to evaluate quality, speed, cost, and stability together.
