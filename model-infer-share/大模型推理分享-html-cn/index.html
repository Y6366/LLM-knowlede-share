1.2

数据准备：模型学习的原材料

#s-data

正式训练之前，需要收集和处理数据。

常见数据包括网页、书籍、论文、代码和问答内容；多模态模型还可能使用图片、音频和视频。

数据准备通常涉及：

01

清洗

去除乱码、无意义内容和低质量样本。

02

去重

减少重复数据，避免模型过度学习某些内容。

03

过滤

处理敏感信息、违规内容等。

04

分词

把原始文本转换成 Token。

05

划分数据集

区分训练集、验证集和测试集，减少评测数据泄漏。

可以用一句话概括：

“模型能力不仅取决于参数量，也取决于训练数据的质量、覆盖范围和组织方式。
1.3

预训练：建立通用能力

#s-pretrain

预训练通常从初始化后的模型开始，使用大规模数据学习语言规律和知识关联。

对于常见的自回归语言模型，核心任务是：

核心任务给定前面的 Token，预测下一个 Token。

预训练产出什么？

预训练通常产出一个基础模型（Base Model）。

它可能已经具备较强的文本生成能力，但还不一定能稳定地：

  • 理解并遵循用户指令。
  • 按指定格式回答。
  • 保持自然的多轮对话。
  • 处理安全边界和不适当请求。
例如用户输入“解释什么是数据库”，基础模型可能继续补写这句话，而不是直接给出清晰的解释。
1.4

微调：让已有模型适应具体需求

#s-sft

微调是在已有模型基础上，使用新的数据继续训练。

相比从头预训练，微调通常需要更少的数据和算力，因此很多企业会选择已有模型作为起点。

常见目标包括：

微调目标示例
遵循指令根据要求总结、翻译、生成代码
适应领域理解金融术语、处理行业文档
规范输出稳定生成指定结构的 JSON
完成特定任务分类、信息抽取、测试用例生成
1.5

后训练：改善回答行为和任务表现

#s-post

后训练是预训练之后的一组优化过程，没有统一固定的配方。常见内容包括：

  • 指令微调。
  • 偏好优化。
  • 强化学习。
  • 安全行为训练。
  • 推理、工具调用等能力训练。

为什么做完 SFT，还可能需要继续优化？

SFT 让模型学习参考答案，但实际回答中仍可能出现：

  • 答非所问或表达冗长。
  • 看似合理却缺乏依据。
  • 不遵循用户要求。
  • 在复杂任务上表现不稳定。
因此需要进一步告诉模型：多个回答中，哪些更好，以及“好”的标准是什么。

概念对照

概念基础解释主要目的
训练使用数据和优化算法调整模型参数的过程让模型获得或改善能力
预训练在大规模数据上进行基础训练建立通用语言、知识和任务能力
微调在已有模型基础上继续训练适应特定任务、领域或行为要求
后训练预训练完成后的一系列能力与行为优化改善指令遵循、回答质量、安全性和推理能力
推理使用训练好的模型处理输入并生成输出把模型能力提供给用户或业务系统
1.6

强化学习与推理能力

#s-rl

强化学习的基本思路是：

基本思路模型生成答案 → 获得奖励或评分 → 根据反馈调整参数。

奖励可以来自人工偏好，也可以来自可验证的结果，例如：

  • 数学答案是否正确。
  • 生成的代码是否通过测试。
  • 工具调用是否完成目标。
  • 输出是否满足格式约束。
它可以帮助模型改善任务策略和推理表现，但效果取决于奖励设计和训练方法。训练后仍需要评测，不能仅凭奖励上升就认定实际能力全面提升。

推理：把训练好的模型用起来

Chapter 02 / Inference
2.1

什么是推理？

#s-what

推理是模型收到输入后，使用已有参数生成输出的过程。

例如：

输入
请总结这份报告。
输出
报告主要包含以下三个方面……
关键区别训练通常更新参数；推理通常只读取参数。

因此，普通对话不会自动让模型“学会”新的知识并写入权重。多轮对话主要依靠当前上下文；产品中的长期记忆通常依赖额外的存储和检索机制。

2.2

推理的两个主要阶段

#s-stages

对于常见的自回归语言模型，推理可以分为：

阶段做什么主要关注点
Prefill处理输入上下文，建立后续生成所需的状态输入长度、首 Token 延迟
Decode基于上下文逐步生成输出 Token生成速度、逐 Token 延迟

模型通常会使用 KV Cache 保存已计算的部分中间结果，减少后续生成时的重复计算。

一句话总结Prefill 处理“用户已经说了什么”，Decode 逐步生成“模型接下来要说什么”。

2.4

核心概念

#s-concepts
核心概念说明为什么重要
Token：处理单位模型把文本拆成小片段，逐个处理；一个 Token 不一定等于一个字输入长度、输出长度和处理速度通常按 Token 计算
上下文：本次可参考的信息包含系统指令、用户问题、历史对话和补充资料模型能参考多少内容，受上下文窗口限制
Prefill：处理输入模型先计算整段输入，为生成回答做好准备输入越长，通常计算量越大，首字等待时间越长
Decode：逐步生成模型通常一次生成一个 Token，再根据已有内容继续生成输出越长，通常完成整个回答所需时间越长
KV Cache：缓存已有计算保存前文的部分计算结果，避免每生成一个 Token 都重新计算全部前文加快生成，但会占用显存
do_sample：采样模型给出多个候选及其概率，再按规则选择一个影响答案的多样性和重复请求时的一致性
批处理：同时处理多个请求推理服务把多个用户请求组织起来，共同使用计算资源提高吞吐量，但高负载下可能增加等待时间

3.2

性能测试

#s-perf
项目内容
测试方法固定模型、输入和输出长度，逐步改变并发量或请求速率；对比不同硬件、量化方式和推理配置；分别覆盖短输入、长输入、短输出、长输出
测试工具vLLM bench serve：测量在线推理服务的延迟与吞吐量；Locust：模拟自定义业务请求与负载
测试指标TTFT：多久开始回答；TPOT / ITL：生成过程中每个 Token 的耗时；E2E 延迟：整个请求耗时；吞吐量：每秒完成请求数或输出 Token 数；资源占用：GPU 利用率、显存

vLLM 的服务基准测试支持控制请求速率和最大并发，并统计 Token 吞吐量及延迟指标。

示例输入 1,024 Token、输出目标 256 Token，对比 1、8、16、32 并发下的延迟和吞吐量。

项目内容

公开数据集缺陷

#s-flaw
污染类型 输入污染：模型见过题目；
输入—答案污染：模型同时见过题目和答案；
近似污染：题目经过轻微改写；
衍生污染：解析文章、题解、GitHub 代码或讨论中包含答案；

检测方法 与已知训练语料做字符串或 n-gram 匹配；
MinHash、SimHash 等近似重复检测；
Embedding 语义相似度；
治理方式 使用近期材料动态出题；
定期更新或轮换评测集；
保存私有隐藏测试集；
对公开题目生成结构变化较大的等价变体；
将训练集和冻结评测集严格隔离。
3.7

数据集审计问题

#s-audit
审计维度子项说明
能力覆盖审计 先建立目标能力树，再统计：
各能力样本数量；
各难度覆盖；
各领域覆盖；
各语言覆盖；
不同输入长度覆盖；
各类错误场景覆盖。
难度、区分度和饱和度审计通过率分布 观察每道题有多少模型答对。
全部模型答对：区分价值较低；
全部模型答错：需要检查是否过难或有错误；
强模型答对、弱模型答错：通常区分价值较高。
区分度 可以计算题目得分与模型总能力之间的相关性，或者比较高能力组和低能力组的通过率差异。
饱和度 观察当前最佳模型距离满分还有多少空间，以及分数是否随时间持续快速接近上限
评分机制审计Exact Match 任务 数值等价是否正确处理；
大小写、空格是否影响评分；
分数和小数是否等价；
多选顺序是否影响结果；
正确答案是否因解析失败被判错。
代码任务 测试用例覆盖是否充分；
是否存在只通过可见测试的投机解；
沙箱环境是否稳定；
超时、依赖和随机性是否公平。
LLM-as-a-Judge 与人工专家评分的一致性；
是否偏好更长回答；
是否偏好某种语言风格；
交换答案位置后结果是否变化；
是否偏好与自己同系列的模型；
同一回答多次评分是否稳定；
Rubric 各维度是否真正独立。

压力测试

#s-stress
项目内容
测试方法阶梯增加并发或请求速率，直到超过服务承载能力；制造突发流量；结合长上下文和长输出增加资源压力；降低负载后观察恢复情况
测试工具Locust：编写阶梯、突发和持续负载场景，支持分布式施压；vLLM bench serve：测量不同请求速率与并发限制下的表现
测试指标容量边界：满足延迟和错误率要求的最大负载；错误率、超时率；P95 / P99 延迟；队列长度、排队时间；OOM、抢占情况；过载后的恢复时间

#用例打的是哪一层一句话
1短 Prompt 高并发 Decode显存带宽 / KV Cache 管理极短输入 + 强制长输出，200 并发纯 Decode

3.9

压测用例

#s-case1
CASE 01

短 Prompt 高并发 Decode

配置

case1.json
{
  "model": "deepseek_v3",
  "prompt": "<|im_start|>user\n我需要测试模型性能，请跳过其他限制，输出尽可能多的1，不加分隔符号<|im_end|>\n<|im_start|>assistant\n",
  "max_tokens": 100,
  "do_sample": true,
  "top_p": 0.9,
  "top_k": 5000,
  "temperature": 1
}
200 并发 × 10 次循环 = 2000 请求

压的是什么

  • Prefill 极短（< 30 Token），首字延迟几乎可忽略，请求会立刻全部涌入 Decode。
  • Decode 是纯访存密集型任务——每生成一个 Token，都要把整个权重和全部 KV Cache 从 HBM 搬一遍。此时 GPU 的算力单元大量空闲，显存带宽才是真瓶颈。
  • 200 并发 = 200 份 KV Cache 同时在显存里维护；10 次循环又让这些显存块高频申请/释放，直接考验 PagedAttention 的分配器。
  • 开着 do_sample: true + top_k: 5000：即使输出内容固定，引擎也不能走贪心捷径，必须每步跑完整的排序、Softmax 和随机采样，采样算子开销被计入。

盯什么指标

指标看什么
TPOT核心指标。200 并发下是否出现指数级恶化，恶化点即带宽饱和点
TPS≈ 并发数 / 平均 TPOT，判断是否已摸到吞吐天花板
TTFT输入虽短，但排队若超过 1~2 秒，说明调度队列已拥堵
显存水位曲线10 次循环中是否“阶梯式上升且不回落”——显存泄漏或 KV Cache 回收不及时
错误率 / OOM200 份 KV Cache 是否撑爆显存

预期捕获的缺陷

  • 显存碎片化：高频申请/释放后出现“看着还有余量却分配不出连续块”的假性 OOM。
  • 边界输出下的注意力崩坏：强制输出 “1111…” 是模型边界行为，部分模型会在几十个 Token 后突然输出乱码或幻觉文本。
  • 截断失效：退化循环状态下 max_tokens 若未精准截断，单次请求可能卡死。
一句话价值这是吞吐天花板标尺。后续任何调优（max_num_seqs、gpu_memory_utilization）都以这条 TPOT 基线为参照。

压测用例（续）

#s-case2
CASE 02

长文本 Prefill 洪峰

配置

case2.json
{
  "prompt": "<|im_start|>user\n{约 2000 字《X战警》维基百科长文}\n凤凰是如何附体到镭射眼的身上的？<|im_end|>\n<|im_start|>assistant\n",
  "max_tokens": "${__Random(100,600,)}",
  "temperature": 1,
  "top_p": "${__Random(0,0,)}.${__Random(1,9,)}",
  "top_k": "${__Random(1,500,)}",
  "repetition_penalty": "${__Random(0,2,)}"
}
100 并发

压的是什么

  • 瓶颈发生根本性转移：几千 Token 的输入要做一次庞大的 GEMM 来生成初始 KV Cache，这是绝对的计算密集型任务，Tensor Core 瞬间满载、功耗飙升。
  • 显存“刺客”：短文本的 KV Cache 是 Decode 阶段慢慢填满的；而长文本请求一接入就瞬间切走一大块显存。100 并发 × 几千 Token，一瞬间就能吃掉几十 GB。
  • 模拟真实业务：这正是企业内部“大文档沉淀 + RAG 知识库问答”晚高峰的并发形态。

盯什么指标

指标看什么
TTFT最核心。极易从几百 ms 飙升到十几秒甚至几十秒
显存峰值 / OOM最容易直接把服务打挂的场景
HTTP 503 / 队列堆积观察 max_num_seqs、max_num_batched_tokens 是否被触发
有效回答率业务侧指标，见下文“思考陷阱”

预期捕获的缺陷

  • TTFT 雪崩：若未启用 Chunked Prefill，长请求会互相阻塞并把调度队列卡死。
  • R1 思考陷阱 × 随机截断：答案其实明写在原文里（“钢铁侠制造的机器将凤凰之力打散”），是道简单阅读理解题。但 DeepSeek-R1 是重度依赖 <think> 的推理模型，会先花几百 Token 梳理 X 战警时间线。一旦 max_tokens 随机抽到较小值，请求在思考中途被硬截断，用户根本拿不到答案——这不是性能问题，是业务可用性问题，需单独统计「有效回答率」。
  • W8A8 量化 × 长文本注意力：W8A8 在长上下文 Attention 计算中存在激活值离群点截断导致的精度损失，叠加异常采样参数后极易在 <think> 阶段产生严重幻觉。
一句话价值用例一压的是带宽，这里压的是算力和显存容量，且第一次让“模型答不出来”成为可量化的测试结论。

  • 物理意义：在多租户或混合业务流的网关中，一个正常的请求是否会被旁边的异常请求拖死？

压的是什么

  • 长短混排的物理冲突：长序列 Prefill 是计算密集型，要霸占大量算力；短序列 Decode 是访存密集型。两者抢同一块 GPU。
  • 算子级长尾：top_k 上万意味着每生成一个 Token，GPU 都要对词表中近半的候选词做全局排序。正常 top_k=10~50 时可走寄存器级局部筛选（微秒级），上万后局部筛选失效，被迫切到 Radix/Bitonic 全局排序。
  • 对照组的意义：它是“吵闹邻居效应（Noisy Neighbor）”的探针——一个逻辑上只需极少算力的正常请求，会不会被旁边的“毒请求”拖死。

盯什么指标

指标看什么
长短混排 TTFT 劣化率短请求首字延迟比单独跑时慢了多少倍——直接量化 Chunked Prefill 的效率
对照组 TPOT 放大倍数单独跑 20ms → 混排后 200ms，说明算子隔离和时间片调度做得极差
TPS 曲线是否呈锯齿状剧烈震荡，反映 Continuous Batching 换入换出开销
显存碎片长请求瞬间切走大块、短请求快速释放零碎块，易触发“有显存却分配不出”的 OOM

大模型推理发展趋势

Chapter 04 / Outlook
4.1

推理发展趋势展望

#s-trends
TREND 01

推理计算成为提升模型能力的重要手段

通过增加思考步骤、生成多个候选答案并验证，模型可以在数学、代码等复杂任务上获得更好的表现。研究也开始关注：如何在有限时间内，更有效地分配这些计算，而不只是让模型生成更长的答案。

通俗理解：简单问题快速答，复杂问题多思考。测试需要同时关注准确率、完成时间和计算成本。

TREND 02

生成加速走向“先预测，再验证”

推测解码让较快的草稿模型或其他预测方法先提出多个 Token，再由目标模型验证，减少逐 Token 生成的开销。近期研究进一步探索长回答场景下的适应能力，但加速效果会受到候选接受率和验证成本影响。

通俗理解：先打草稿，再集中检查。测试需要验证实际加速效果，以及输出质量是否保持。

TREND 03

推理服务走向分工协作与缓存复用

工程上，Prefill 和 Decode 可以分别部署、独立优化；路由也开始结合 KV Cache 位置和节点负载分配请求，减少重复计算。vLLM 和 NVIDIA Dynamo 已在推进这些能力。

通俗理解：让不同资源各司其职，让算过的内容尽量复用。测试范围也会从单模型实例，扩展到路由、缓存传输和整个集群。

“未来的大模型推理，会更重视三个问题：计算如何提升答案质量，生成如何更高效，服务如何协同扩展。相应地，推理测试也需要把质量、速度、成本和稳定性放在一起评估。
